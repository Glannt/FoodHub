§2Ba thay đổi nên làm ngay Làm luôn

A · Unique index + CHECK constraint

CreateRestaurantHandler.cs:22-24 đã tự thừa nhận race condition: hai request song song cùng thấy "chưa có" rồi cùng INSERT. Comment ghi "sẽ xử lý ở Giai đoạn 2" — nhưng nó rẻ, làm luôn được.

Thêm vào RestaurantConfiguration.cs: 

// CHECK: phòng thủ chiều sâu cho tọa độ.
// FluentValidation ở tầng Application chỉ chặn được request đi qua HTTP.
// Script SQL, job nền, import CSV đi thẳng vào DB và không qua validator.
// Dùng ToTable(..., t => ...) chứ không dùng HasCheckConstraint trực tiếp:
// EF Core 8+ đánh dấu cách thứ hai là obsolete.
builder.ToTable("restaurants", t =>
{
    t.HasCheckConstraint("ck_restaurants_latitude",   "latitude   >= -90  AND latitude   <= 90");
    t.HasCheckConstraint("ck_restaurants_longtitude", "longtitude >= -180 AND longtitude <= 180");
});

// UNIQUE: khóa cái race mà comment ở CreateRestaurantHandler tự ghi nhận.
builder.HasIndex(r => new { r.Name, r.Address })
       .IsUnique()
       .HasDatabaseName("ux_restaurants_name_address");

Thêm vào MenuItemConfiguration.cs: 

builder.ToTable("menu_items", t =>
    t.HasCheckConstraint("ck_menu_items_price", "price > 0"));
Xoá index thừa

Xoá builder.HasIndex(r => r.Name) ở dòng 45 của RestaurantConfiguration. Unique index (name, address_text) đã phục vụ được mọi truy vấn lọc theo name nhờ leftmost prefix — giữ lại chỉ tốn thêm ghi mà không tăng tốc gì.

Đã chốt: handler giữ nguyên 4 cột, không sửa

Handler tiếp tục check 4 cột (name + address_text + latitude + longtitude). Unique index 2 cột đóng vai trò lưới an toàn cuối cùng, không phải bản sao logic handler.

Hai tầng này không mâu thuẫn, chúng bảo vệ hai thứ khác nhau:

Tầng Chặn trường hợp Trả về
AnyAsync 4 cột Người dùng gõ đúng tên + địa chỉ + toạ độ giống hệt bản cũ 409 Conflict — thông báo rõ ràng, có thể hiện form
Unique index 2 cột Hai request chạy song song, cùng thấy "chưa có" rồi cùng INSERT 500 từ Postgres — lỗi hệ thống, log để điều tra

Điểm mấu chốt: nếu đưa toạ độ vào unique index, một lần đo lại GPS lệch vài chữ số thứ tư sẽ tạo bản ghi trùng mà handler không chặn được. Giữ index 2 cột đúng nghĩa là GPS đo lại vẫn bị chặn — đúng ý. Còn việc hai quán cùng tên cùng địa chỉ nhưng khác toạ độ là chuyện hiếm, và xử lý bằng cách sửa tên ở UI quản trị.

Rủi ro btree row size

Unique index trên address_text varchar(500) có thể vượt giới hạn 2704 byte của index row nếu ai nhập địa chỉ 500 ký tự tiếng Việt có dấu (mỗi ký tự 2–3 byte UTF-8). Lỗi sẽ là index row size exceeds btree version 4 maximum. Cách thoát: hạ xuống varchar(300), hoặc tạo cột sinh tự md5(name || address_text) và unique index trên cột đó.

B · Lọc IsApproved trong GetRestaurantsHandler

Hiện tại handler ToListAsync() toàn bảng rồi trả về tất cả, không có điều kiện nào về IsApproved. DB có 1 nhà hàng is_approved = false và GET /api/restaurants trả chính nó về cho khách.

Một dòng, chèn ngay sau .AsNoTracking():

.Where(r => r.IsApproved)   // nhà hàng chưa duyệt không được hiện ra
Không sửa riêng lẻ

Handler này đang chờ bạn viết lại cho phân trang. Filter phải chạy trong DB (đặt Where trước Skip/Take) chứ không lọc trong RAM như hiện tại. Đặt sẵn dòng này thì lúc bạn viết lại không phải nghĩ lại.

C · Migration

dotnet ef migrations add AddRestaurantConstraintsAndUnique -p src\FoodHub.Infrastructure -s src\FoodHub.Api
Đọc file Up() trước khi áp

Phải xác nhận nó sinh ra CreateCheckConstraint + CreateIndex (với isUnique: true), không phải DropColumn + AddColumn. Cột đang tồn tại; nếu thấy hướng sai thì xoá file migration và tạo lại. 

dotnet ef database update -p src\FoodHub.Infrastructure -s src\FoodHub.Api

Kiểm chứng:

docker exec dev-postgres psql -U glantt -d FoodHub -c "\d restaurants"

Kỳ vọng thấy ck_restaurants_latitude, ck_restaurants_longtitude, và index ux_restaurants_name_address.

§6Exception · Middleware · Behavior mới

Loại File Status Khi nào dùng
Exception ForbiddenException 403 Sửa nhà hàng không phải của mình
Exception BusinessRuleException 422 State machine từ chối chuyển trạng thái — "đơn đang Preparing không huỷ được"
Middleware ForbiddenExceptionHandler 403 Bọc ForbiddenException thành ProblemDetails
Middleware BusinessRuleExceptionHandler 422 Idem
Behavior TransactionBehavior — Bọc SaveChangesAsync trong transaction. Chỉ Command
TransactionBehavior — hai cái bẫy

1. Phải kiểm tra request là IRequest (Command) hay IRequest<T> (Query). Query không mở transaction.

2. Nếu handler đã tự gọi SaveChangesAsync thì transaction đã commit trước khi behavior kịp bọc. Với PlaceOrder phải chọn một trong hai: bỏ unitOfWork.SaveChangesAsync khỏi handler, hoặc để behavior lo.

Thứ tự đăng ký behavior

Đăng ký đầu = bọc ngoài = chạy trước. Thứ tự hiện tại đã chốt trong DependencyInjection.cs: validation → logging → transaction → cache.

§9Bẫy thường gặp

Bẫy đã mắc rồi

  • Validator internal → bị bỏ qua im lặng
  • CreatedAtAction(nameof(Create)) → 500 sau khi đã insert
  • [property: Required] trên positional record → MVC ném exception
  • decimal cho toạ độ + client bỏ field → ghi 0.000000
  • Chạy dotnet ef khi build đang lỗi → scaffold từ DLL cũ
  • Indexer (user_id, is_default) không thay thế partial unique index

Bẫy sẽ gặp ở GĐ2

  • Query cũng bị bọc transaction nếu không kiểm tra Command/Query
  • Handler tự SaveChangesAsync làm transaction của behavior vô hiệu
  • CASCADE xoá luôn lịch sử đơn hàng
  • Trộn món 2 nhà hàng vào 1 giỏ
  • Đọc giá từ menu_items khi hiển thị đơn cũ
  • UseAuthentication sau UseAuthorization
  • Vote task.WhenAll trên cùng một AppDbContext
